# План Journal 1.0.2-beta.2

Статус — согласованный план разработки. На момент составления основной релиз — `1.0.1`, текущая бета — `1.0.2-beta.1`, целевой предрелиз — `1.0.2-beta.2`.

**Две независимые галереи iOS.** При каждом новом опубликованном стабильном релизе автоматически собирать его галерею. Галерею последней опубликованной беты собирать или переснимать только по желанию владельца через ручной запуск в GitHub Actions. Оба канала используют один фиксированный сценарий. В ветке `screenshots` хранить их рядом: `pack/stable/` и `pack/beta/`. Выпуск RC или черновика съёмку не запускает.

## 5. Две галереи iPhone с фиксированным составом

### Когда и из чего собирать

| Канал | Запуск | Откуда брать приложение и брендинг | Куда публиковать |
|---|---|---|---|
| Стабильный | Автоматически после успешной публикации каждого нового стабильного выпуска. Вручную можно повторить сборку. | Последний опубликованный стабильный GitHub Release с тегом `vX.Y.Z`. Зафиксировать тег и SHA до съёмки. | `screenshots:pack/stable/` |
| Бета | Исключительно через **Actions → Пак скриншотов Journal → Run workflow → beta**. Выход новой беты или стабильного релиза сам по себе эту галерею не меняет. | Самая новая по числовой версии и номеру беты опубликованная сборка вида `vX.Y.Z-beta.N` с признаком prerelease. Исключить черновики, RC и удалённые выпуски. | `screenshots:pack/beta/` |

- Ручной запуск принимает `channel=stable|beta` и `force_rebuild=false|true`. Обычный запуск собирает отсутствующую, неполную или устаревшую галерею выбранного канала. При совпадении версии, SHA, спецификации съёмки и контрольных сумм завершает работу до запуска симулятора. Флаг позволяет явно переснять текущую версию. При отсутствии опубликованной беты показать причину и сохранить файлы обоих каналов.
- Автозапуск привязать к завершению штатного Release с проверкой фактически опубликованного тега. Учесть, что создание GitHub Release самим workflow с `GITHUB_TOKEN` не гарантирует запуск второго workflow через `release.published`. Успех сборки беты/RC и повтор старого выпуска не должны инициировать съёмку стабильного канала.
- В каждой подпапке одинаковая структура: `ios/light/`, `ios/dark/`, `frames/`, `mockups/`, `README.md` и `manifest.json`. В корне `pack/` разместить указатель на каналы с фактическими версиями. При переходе со старой структуры переместить проверенный стабильный комплект в `pack/stable/`, обновить читателей манифеста, документацию и ссылки в одном согласованном переходе. Общий ZIP ветки содержит обе доступные подпапки.

### Фиксированные значения и сценарий

- Зафиксировать в репозитории общую спецификацию `gallery-v1` и один офлайн-набор данных `trade-0000-v1`. Обе версии приложения открывают один и тот же учебный день: **среда, 18 ноября 2026, 11:10, Europe/Minsk**, группа **0000**, русский интерфейс, портрет, масштаб текста 100%, системное время 11:10, полный сигнал и заряд 100%. Эталон v1 — **iPhone 17, iOS Simulator 26.2, 1206 × 2622**. При недоступности профиля остановить съёмку с пояснением. Смена устройства или набора экранов требует явной новой версии спецификации.
- На эталонный день зафиксировать четыре пары: 08:20 — математика, ауд. 201; 10:10 — товароведение продовольственных товаров, ауд. 214; 12:20 — экономика организации, ауд. 227; 14:10 — товароведение непродовольственных товаров, ауд. 240. В 11:10 идёт вторая пара. Сверить названия с официальным расписанием МГТЭК, использовать расшифровки Journal и сохранить ссылку с датой сверки. Преподаватели вымышлены, например «И. И. Иванова». Реальные расписания групп и персональные назначения не переносить.
- Сохранить конкретные записи и идентификаторы в общей фикстуре: расписание за −28…+14 дней, историю баллов по 10-балльной шкале, уважительные и обычные пропуски, пометку «Проверочная работа» на второй паре и четыре задания торгового профиля, одно из них выполнено. Значения после первоначального создания фикстуры неизменны при повторных запусках; текущие дата, сеть и генератор случайных чисел на результат не влияют. Средние баллы и суммы часов вычисляет приложение. В форме предмета открывать математику, в деталях пары — вторую пару эталонного дня; редактируемые записи задавать по фиксированным ID.
- Для каждого кадра сохранить в спецификации исходную вкладку, выбранную дату/запись, положение прокрутки, открытый лист, тему и ожидаемый видимый элемент. Перед захватом проверить состояние и дождаться завершения анимации. Неподдерживаемую сцену считать ошибкой с её ID. Это исключает случай, когда в комплекте верное количество файлов, но снят дважды один экран.

### Одинаковая подача и публикация

- На один канал: **114 оригиналов + 228 кадров в корпусах + 2 самостоятельные прозрачные PNG-рамки + 4 фирменных макета = 348 изображений**. Вместе с README и манифестом — 350 файлов внутри подпапки канала.
- Сохранить три тематические композиции в дополнение к главной обложке: **«Ход дня»** — 1600 × 1000, светлая главная в светлом корпусе; **«Расписание»** — 1200 × 1500, тёмное расписание в тёмном корпусе; **«Оценки и пропуски»** — 1600 × 1360, светлые оценки и тёмные пропуски рядом. В обоих каналах одинаковые кадрирование, отступы и компоновка; логотип и интерфейс соответствуют тегу приложения.
- На витринах показывать пять PNG в порядке: главная (светлая), расписание (тёмная), оценки (светлая), пропуски (тёмная), задания (светлая). Корпус совпадает с темой. Страница основной установки и стабильный источник читают стабильную подпапку, бета-источник — бета-подпапку при совпадении тега. Пока последнюю бету не снимали, для бета-источника сохранить пять стабильных кадров с явной подписью их версии; каталог установки и обновления беты остаётся доступным.
- Манифест каждого канала содержит канал, тег, SHA приложения, версии и контрольные суммы спецификации и фикстуры, модель, iOS, разрешение, список сцен и SHA-256 файлов. Собирать во временном каталоге, проверять точные имена, количество и размеры, прозрачность и отсутствие дублей имён. Перед публикацией повторно сверить последнюю версию выбранного канала. Сериализовать записи в общую ветку, начинать с актуальной вершины и заменять только свою подпапку, затем обновлять корневой указатель. При ошибке сохранять оба прежних комплекта.

### Главная обложка Journal — три экрана одного учебного дня

**Назначение.** За один взгляд человек должен увидеть, что показывает Journal прямо сейчас, где посмотреть следующую пару и где хранятся оценки. Главная обложка — четвёртый макет каждого канала. Входы — три уже снятых кадра из того же пака. Дополнительных сцен в матрице съёмки не требуется.

1. **Сюжет и порядок устройств.** Слева — тёмное «Расписание» в графитовом корпусе (`dark/schedule-framed-dark.webp`), в центре на переднем плане — светлая «Главная» в серебристом корпусе (`light/home-default-framed-light.webp`), справа — светлые «Оценки» в серебристом корпусе (`light/grades-framed-light.webp`). Все пути относительны к `ios/` текущего канала. Центр композиции — крупное число минут на главной. В левом кадре должны читаться время и название пары, в правом — средний балл и диаграмма. Интерфейс вставлять целиком из проверенного мокапа с реальной версткой приложения.
2. **Брендинг и текст.** В верхнем левом углу поставить нативную иконку из тега канала и слово **Journal**. Основной слоган крупно: **«От первой пары до последней оценки»**. Зафиксировать короткий вариант для текстового анонса или компактной подписи: **«Пары и оценки под рукой»**. На самой обложке использовать один основной слоган. В мобильной вёрстке допускать перенос после «пары». Шрифт с полноценной кириллицей, спокойное полужирное начертание, достаточный контраст. Названия разделов уже видны на экранах, поэтому отдельные плашки над телефонами не нужны.
3. **Композиция.** Один мастер 1800 × 1200 px (3:2). По краям оставить минимум 72 px. Верхнюю четверть отдать логотипу и слогану, нижнюю часть — трём устройствам. Центральный iPhone занимает около 67% высоты холста, боковые — около 57%; центры по горизонтали — 50%, 25% и 75% соответственно. Боковые поставить чуть ниже центрального. Сохранить естественные пропорции устройств, одинаковое направление света и мягкую контактную тень. Фон — светлая нейтральная поверхность; за центральным телефоном одно широкое тональное поле из стандартной палитры Journal. Реалистичные блики остаются на корпусах, текст и экран лежат на спокойном фоне. Все три силуэта, навигация и смысловые области целиком помещаются в кадр.
4. **Сборка и размещение.** В генераторе макетов добавить композицию `overview`. После готовности трёх входных изображений формировать `pack/stable/mockups/overview.webp` или `pack/beta/mockups/overview.webp`, включать файл в манифест и проверку SHA-256. Показывать обложку первой в README канала. В README проекта и на основной странице установки использовать опубликованный stable-мастер. В карточках каталогов формировать обложку источника из соответствующего мастера, с экспортом 1200 × 800 без обрезки; для беты применять существующее правило совпадения тега и подписанного стабильного резерва. Пять индивидуальных PNG остаются отдельной лентой для подробного просмотра. Для анонсов использовать тот же мастер и короткий слоган. Производные изображения витрин хранятся в публикации сайта и не увеличивают число файлов в паке.
5. **Приёмка.** Проверить мастер при 100%, экспорт 1200 × 800 и превью шириной 360 px в светлом и тёмном окружении. На мобильном превью должны различаться три устройства, Journal, слоган и крупные часы; мелкие записи можно рассмотреть на отдельных витринных кадрах. На полном размере сверить детали экранов, отсутствие двойных рамок, артефактов прозрачности, обрезанных углов и пересечений текста с корпусами. Проверить ссылки на обе обложки после публикации соответствующих каналов. Для README и сайта задать описание: «Journal на трёх iPhone: расписание, отсчёт до конца пары и журнал оценок».

## 7. Проверить, выпустить бету и принять результат

- **Интерфейс.** Автоматически проверить 20 тем × 2 режима и системный цвет с запасным вариантом. Для стандартной, красной и монохромной схем сравнить ключевые состояния визуально. Проверить узкий телефон, широкий экран, крупный текст, клавиатуру и озвучку. Проверка кадров в рамках QA беты не запускает сборку публичной галереи.
- **Функции и обновление.** Пройти выбор группы, расписание и офлайн-кэш, создание и редактирование оценки, пропуска, задания и пометки, удаление и отмену. Запустить анализатор, тесты Flutter, архитектурные проверки и нативные сборки. Проверить обновление поверх предыдущих сборок, чтение старой резервной копии, выбор иконки и номер версии в настройках.
- **Публикация приложения.** После успешных проверок выпустить APK и IPA как `1.0.2-beta.2` с возрастающим номером сборки. Проверить предварительный статус GitHub Release, установку и бета-подписку. Основным выпуском остаётся `1.0.1`. Публикация беты может обновить метаданные каталога; процесс съёмки не запускается.
- **Публикация галерей.** Перенести действующий стабильный комплект и вручную пересобрать стабильную 1.0.1 по новой спецификации. Владелец может отдельно запустить съёмку последней беты. Публикация 1.0.2-beta.2 сама по себе не создаёт и не обновляет её пак.
- **Финальная приёмка.** Проверить маршрутизацию событий нового stable, beta, RC и черновика. Автоматически снимается только новый stable. Ручной beta выбирает последний опубликованный бета-тег. Для каждого канала проверить совпадение 57 × 2 сцен, фиксированных данных, 348 изображений, главной обложки с тремя экранами, пяти витринных PNG и SHA-256. Проверить пропуск готового пака, принудительную пересъёмку, одновременные запросы и сохранность соседней подпапки при успехе и ошибке. Сверить скачанный ZIP и публичные ссылки с обоими манифестами.
